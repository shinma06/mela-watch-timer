# mela 再構築の受入条件と実装順序

仕様版1.0、2026-10-02。[要件](requirements.md)と[技術設計](timer-design.md)に対応する。**以下は実装時に実行する試験であり、この文書を作成した時点の合格報告ではない。**

## 実装順序

各段階は1つのIssueとwriterで管理し、専用branch/worktree・PR・独立レビューを使う。順序が前後しても、最後に全要件を確認する。別Issueへ残条件を移す場合は担当、具体的な操作、期待結果、再開条件を双方向リンクで残す。

| 段階 | 実装内容 | この段階の終了条件 |
| --- | --- | --- |
| 1 技術基盤と状態 | Issue #3との担当調整、Swift 6、test target、値型の状態遷移、時計の注入 | Debug/Release build、状態と境界時刻のテストが成功。旧機能を完成扱いしない |
| 2 保存と通知 | atomic保存、復元、通知worker、許可、古い通知の除去、通知アクション | 保存失敗・復元・遅いaddの回帰テスト成功。通知の実機試験を始められる |
| 3 新しい画面 | 2色Shape、操作sheet、初回案内、設定、VoiceOver、Always On | 画面見本と幾何が一致。全操作が新モデルへ接続。旧モデル・旧UIを削除 |
| 4 記録と品質 | 7日分の記録、削除、エラー文言、端末サイズ、電池・復帰確認 | 全自動試験、実機試験、利用体験の評価を実施し、重大な不成立がない |
| 5 配布準備 | アイコン・表示名・日本語文言・version・署名・配布説明を整合 | 実装完了ゲートを満たし、配布に必要な利用者判断を別に確認できる |

段階1〜3で失敗の根本を直し、旧Viewに新たな例外処理を積み足さない。配布そのものやApple側の審査完了は、要件書作成・PR mergeの完了には含めない。

## 自動試験

Swift Testingで以下の結果を確かめる。同じ仕組みの入力違いはparameterized testへまとめ、テストのためだけのframeworkは導入しない。通知・保存の失敗は小さなfakeまたは一時ディレクトリで作る。実時間を待たず、テストごとに独立した状態を使う。

| ID | 入力・操作 | 必須の結果 |
| --- | --- | --- |
| A01 開始と連打 | ready focus 1500秒でstartを2回 | Sessionと期限は1つ。2回目で延長・再作成しない。開始成功の副作用も1回 |
| A02 pause/resume | 1500秒を開始、10.4秒後pause、100秒後resume | 残り1489.6秒。pause中に減らず、resumeから1489.6秒後が期限。分母は1500秒 |
| A03 期限の境界 | 期限−0.001秒、期限と一致、期限＋0.001秒を与える | 前者はrunning、残り2つは完了。集中記録1件、次はrest ready。pause入力と同時でも完了優先 |
| A04 やり直しと切替 | 期限前のrunning/pausedをやり直す・切り替える | 集中記録0件。元Sessionを破棄し、指定phaseのready。自動開始・完了触覚なし |
| A05 設定の適用 | 25分開始後に集中50分へ変更。pause/resume。その後やり直し | 現在のSessionは1500秒のまま。やり直し後のreadyは3000秒。保存取消しなら25分のまま |
| A06 入力検証 | 集中0/121、小数分、不正enum、NaN/∞、休憩0/61 | 実行可能な状態として採用しない。正しい最小・最大値は通る |
| A07 復元 | runningを5分後と期限10分後に別モデルへロード | 期限前は正しい残り。期限後は1回だけ完了し、後続フェーズは進めない。pausedは変化なし |
| A08 完了の冪等性 | Task、active復帰、通知、再起動の順で同じ期限を処理 | 集中記録1件、lastCompletionは同じID。履歴追加と状態変更が同じ保存snapshotに入る |
| A09 保存失敗 | start/pause/complete/settings/deleteでwrite失敗を注入 | 技術設計の失敗表どおり。start失敗で通知なし。pause失敗は継続を明示。完了再試行で重複なし |
| A10 addと取消しの競合 | add待ちの間にpause。pause完了後にadd成功を返す | 古いIDを補償削除。pause後に有効なpendingなし。Task.cancelだけに依存しない |
| A11 通知アクション | 有効な完了通知を2回操作。その後古い回・不正payloadを操作 | 最初だけ次Sessionを開始。古い／重複／不正通知は現在の状態を破壊しない |
| A12 幾何 | r=1/0.75/0.5/0.25/0と複数の縦横比 | 全画面中心、対角半径、要件の各象限と色が一致。角に意図しない空白なし。0/1に細い残り線なし |
| A13 通知の再照合 | 許可拒否、音だけ無効、通知オフ、許可要求のエラー | タイマーは使える。拒否とエラーを区別。オフで予約なし。音の無効を独自触覚で迂回しない |
| A14 世代の競合 | 古いadd保留→pause→resume→新add成功→古いadd成功/失敗 | 最新tokenの通知だけが有効。古い結果が新しい通知を消さず、エラー状態も汚さない |
| A15 期限と通知予約 | add前に残り0、微小な正の値、期限後の復元、現在回のadd失敗 | 0以下のtriggerなし。正の値を扱える。過去の通知を再予約しない。失敗で計時を巻き戻さない |
| A16 終了の通知経路 | 前景Task→willPresent、willPresent→Task、通知なし、inactive中の完了 | 有効な予約があれば独自終了触覚0回。fallbackは条件内で1回まで。復帰時の鳴らし直しなし |
| A17 集計 | 23:59開始・翌日完了、pause、途中破棄、重複ID、TZ変更、削除、14日超 | 完了日へdurationを1件。pause/破棄を水増ししない。7日表示、14日保持、削除後の新規完了は記録 |
| A18 migrationと破損 | ファイルなし、壊れたJSON、未知schema、旧通知ID、初期化失敗 | 無断の上書きなし。旧通知を除去。確認済み初期化だけ新規状態。退避失敗時も元データを破壊しない |
| A19 時計変更 | 同一プロセスでwall clockを±1時間。新プロセスでは期限差を与える | 前者は経過時間が不変。後者は明記したfallback範囲内。TZだけの変更で残り不変 |
| A20 終了後の通知保持 | foreground完了を保存してから、期限通知を配信 | 完了処理が予約を先に消さない。同じIDは有効。次のstart・通知オフでは無効化される |

※ fakeによるadd成功は、実機で鳴るという証拠にはしない。A12の幾何確認も、実画面のsafe areaやOS表示の確認を代替しない。

## buildと実行コマンド

現時点のprojectにtest targetはない。段階1でwatchOS unit test targetを追加し、共有scheme `mela-watch-timer Watch App`のTest actionへ登録してから以下のtestを実行可能にする。成功を主張する前に、testが0件ではなく上表のケースを実際に走らせたことを確認する。

実行前に`DEVELOPER_DIR`を使用する安定版XcodeのDeveloperディレクトリへ設定する。グローバルなxcode-selectは無断変更しない。Simulator起動・GUI操作は[GUI運用](operations.md)の予約と実際の権限に従う。

```bash
# 前提の確認
: "${DEVELOPER_DIR:?使用するXcodeのDeveloperディレクトリを設定してください}"
xcodebuild -version
xcodebuild -showsdks
xcodebuild -list -project mela-watch-timer.xcodeproj

# DebugとReleaseのSimulator build
xcodebuild -project mela-watch-timer.xcodeproj \
  -scheme 'mela-watch-timer Watch App' \
  -configuration Debug \
  -destination 'generic/platform=watchOS Simulator' \
  -derivedDataPath .harness-local/DerivedData \
  CODE_SIGNING_ALLOWED=NO build

xcodebuild -project mela-watch-timer.xcodeproj \
  -scheme 'mela-watch-timer Watch App' \
  -configuration Release \
  -destination 'generic/platform=watchOS Simulator' \
  -derivedDataPath .harness-local/DerivedData \
  CODE_SIGNING_ALLOWED=NO build

# test target追加後。実在するSimulator IDと未使用の結果名を指定
: "${MELA_WATCH_SIMULATOR_ID:?試験に使うwatchOS Simulator IDを設定してください}"
: "${MELA_RUN_ID:?この試験の一意な結果名を設定してください}"
xcodebuild -project mela-watch-timer.xcodeproj \
  -scheme 'mela-watch-timer Watch App' \
  -configuration Debug \
  -destination "platform=watchOS Simulator,id=${MELA_WATCH_SIMULATOR_ID}" \
  -derivedDataPath .harness-local/DerivedData \
  -resultBundlePath ".harness-local/TestResults-${MELA_RUN_ID}.xcresult" \
  CODE_SIGNING_ALLOWED=NO test

# docs・開発ハーネスの整合。アプリ試験とは別
python3 scripts/check.py
```

加えて、サポート下限26.4の利用可能なruntimeと、採用した27.xのruntime／実機で互換性を確認する。SDKが新しいことだけでは26.4での実行確認にならない。利用できないruntimeはblockedとして明記し、実機または利用可能な検証環境を次の担当へ引き継ぐ。

既存CIの`harness-checks`はアプリのbuild/testを実行しない。実装担当は利用可能なmacOS＋Xcode経路で上記結果をPRへ添付する。CIへ追加する場合も、実在するrunner／SDKで動作を確認してから必須化し、架空のrunner labelを指定しない。

## 画面と実機の試験

実機には、最小クラスのサポート画面と最大クラスの画面、Always On対応機を含める。所有端末だけで満たせない画面サイズはSimulatorで補完し、実機を用意できない条件を明記する。触覚・通知の合否は実機で確認する。

各記録にsource SHA、アプリbuild、OS build、端末クラス、通知許可、消音・触覚・Focus・低電力・装着状態、操作と時刻、期待と実測、担当を付ける。端末IDや個人情報は公開記録に載せない。

| ID | 初期条件と操作 | 期待する結果 |
| --- | --- | --- |
| M01 全画面 | 小・大の画面で各phaseの100/75/50/25/0%を表示 | 円の中心が全画面中心。上下safe areaでずれない。角まで2色。中心UIなし。OS表示との区別を記録 |
| M02 Always On | 計時中に腕を下げ、1分後と期限後に上げる。AODオフ・低電力も確認 | 低輝度の2色、過剰な更新なし。再表示時は最新状態。画面消灯や時計画面への復帰はOS仕様として区別 |
| M03 基本操作 | start→pause→時間をおく→resume→自然完了→次を手動開始 | 操作sheetと2色面が仕様どおり。pause中は減らない。終了で勝手に次が進まない |
| M04 設定と記録 | 1分の集中を完了、途中破棄、設定変更、記録削除 | 自然完了だけ回数と時間に反映。現在回の分母は変わらない。削除に確認があり、実行中は保たれる |
| M05 バックグラウンド | 集中を開始し別アプリへ。期限前、期限直後、長時間後に戻る | 残りが正しい。期限後は1回完了。架空の複数セッションなし |
| M06 終了・再起動 | running/pausedでアプリを終了し再起動。別試行でWatch再起動 | runningは期限から復元、pausedは固定。履歴二重追加なし。再起動中の配信は別途実測し、無条件保証しない |
| M07 正常な通知 | 装着・通知許可・触覚オン・Focusオフで、アプリ前景／背景それぞれ1分計時 | 1回の終了について1件の通知。前景は独自終了触覚を追加しない。本文は操作を開き、明示actionだけ次を開始 |
| M08 設定別の通知 | OS拒否、アプリ通知オフ、soundオフ、消音、触覚オフ、Focusオン、非装着／ロックを個別に試す | 計時は維持。各設定を迂回しない。見落とし・遅延の条件を記録。許可要求を繰り返さない |
| M09 取消しと重複 | 開始直後pause/resumeを連続操作。期限付近でpause。通知を何度も操作 | 新しい回の通知だけが有効。古い通知から誤開始なし。OSが既に配信した境界事象とアプリの二重予約を区別 |
| M10 アクセシビリティ | VoiceOver、最大Dynamic Type、Reduce Motionで基本操作と設定・記録へ移動 | 読み上げでphase・残り・状態が分かる。毎秒読み上げない。すべての操作に到達でき、押し間違えにくい |
| M11 見分けと方向 | 赤青の境界、低輝度、日中・暗い場所、左右の手首・表示方向を確認 | 主画面の中心がずれず、基本の割合を判別できる。難しい場合は操作画面とVoiceOverが代替になる |
| M12 単体利用 | iPhoneとの接続とネットワークを切り、設定→集中→通知→記録を行う | 通信・ログイン要求なし。ローカル計時・保存・通知に外部接続が不要 |
| M13 時計変更 | 同一プロセス中にwall clock/TZを変更。別試行で終了後に時刻変更 | 同一プロセスの残りは不変。新プロセスは定義したfallbackどおり。通知の実挙動を記録 |
| M14 電力と反応 | Releaseで25分集中＋5分休憩。主画面・AOD・別アプリを使い分け、Instrumentsで確認 | 無限loop・背景の毎秒処理・毎秒保存なし。下記性能基準を満たす |
| M15 旧版更新 | 旧版で通知を予約した状態から新版をインストールし初回起動 | 旧通知IDが消え、新旧通知が重ならない。初期設定25/5。架空の旧履歴を生成しない |

強制終了後・再起動中・OSが通知を抑制する条件は、配信不能や遅延があり得る条件として実測する。アプリを起動した後の復元と古い通知の安全性は、それらの条件でも必須である。

### 性能と品質の設計基準

以下の数値は本製品が置く受入目標であり、watchOSの公式保証値ではない。端末・build・測定方法と一緒に結果を残す。

- activeでCPUが実行できる状態では、面の残りと基準時刻の差を1秒以内にする。前景復帰後は1秒以内に最新の面と状態へ同期する。
- 通常のタップから操作画面または押下応答が見えるまでを目標300ms以内とする。通知登録待ちを理由にpause・取消しの操作を数秒止めない。
- Releaseの通常計時では面の更新は最大毎秒1回、paused／readyのperiodic更新は0。永続化は操作・状態遷移時だけ。
- 背景の維持に使うaudio・location・workout・extended runtime sessionは0。ネットワークリクエストは0。
- 30分の基本シナリオでクラッシュ・未処理例外・Sessionの重複・記録の欠落がない。繰返し操作後にTaskやモデルの数が増え続けない。
- 通知はM07の正常条件で前景10回・背景10回を測り、早発0回、二重通知0回、各条件で少なくとも9回が期限後5秒以内を品質目標とする。残りの配信遅延も記録し、通知未着は不合格。これは利用時の配信保証ではない。
- 電池消費は同じ端末・画面設定の待機時とアプリ利用時を比較して記録する。短時間の残量表示だけで「低消費」と断言しない。明らかな発熱や継続CPU負荷があれば原因を解消して再測定する。

OS由来の制約で品質目標を満たせない場合、アプリの実装不具合と混同せず、再現条件とユーザー体験への影響を示す。ただし未着や頻繁な遅延が残るまま「終了を知らせる」体験が成立したとはしない。

## 実機検証で確認する成立条件

未決の機能を実装者へ投げるためのリストではない。決定済みの仕様が公開APIと端末上で成立するかを確かめるゲートである。

| ゲート | 採用済みの方式 | 不成立の場合の次の操作 |
| --- | --- | --- |
| 全画面の中心・角 | safe areaを無視した背景＋対角半径のShape | レイアウトを修正する。中央への情報追加で埋め合わせない |
| 前景の終了感知 | 通知のsoundと面の変化。独自終了触覚を重ねない | delegate設定・許可・配信を点検。必要なら方式変更の影響を仕様と試験へ反映する |
| 消音時の区切り | OSの触覚設定に従う | OS設定説明を見直す。任意の強制振動ができると説明しない |
| AODでの理解 | 低輝度2色、OS cadence、再表示時同期 | 色を調整し、OSの表示制約は明示。常時前景の偽装はしない |
| 時計変更・端末再起動 | monotonic＋保存期限のfallback | 定義との差を修正。OS通知の保証を後付けしない |
| 最低OSとSwift 6 | 26.4対応API＋採用SDKでのbuild/test | 互換を修正。最低OSを変える必要があれば対象端末と理由を明記して仕様改訂 |

アプリ固有の不具合が残る場合はfail。端末や実行環境がなく確認できない場合はblocked。まだ実施していない場合はpending。いずれもpassに読み替えない。

## 利用体験の評価

機能が動くだけで、数字を置かない価値が確かめられたことにはならない。実装担当とは別の試用者を含む3人を目安に、短い評価を行う。参加者の確保ができない場合は未実施として残し、推測で評価結果を埋めない。

| 観察すること | 手順 | 判断基準 |
| --- | --- | --- |
| 操作の発見 | 初回案内を1回読んだ後、集中を開始・pause・resumeしてもらう | 追加説明なしで各操作に到達できる。詰まった場合は案内と操作画面を修正 |
| おおよその残り | 75/50/25%をランダムに各phaseで示す | 「多い・半分・少ない」を全員が区別できる。色名だけの暗記を求めない |
| 集中の邪魔にならない | 実際の作業で25分または本人に合う設定を1回使う | 中間通知・画面の点滅・勝手な開始による中断がない。数字がない不安は聞き取り記録 |
| 区切りに気づける | 通常の装着・通知設定で前景と背景の終了を体験する | 気づいた時刻と見落としを記録。繰り返す見落としは通知ゲートへ戻す |
| 記録の理解 | 途中破棄と自然完了を1回ずつ行い記録を見せる | 「完了した集中」の回数・時間と理解でき、全作業時間と誤解しない |

少人数の試用を生産性向上の統計的な証明とは扱わない。見つかった操作上の問題を直すために使う。

## 実装完了と配布の判定

### 実装完了

- P01〜D01の必須要件が実装され、上表の自動試験と必要なbuildが成功している。
- 必須の画面・実機条件を確認し、アプリ固有の未解決欠陥がない。OSの制約は利用者向け説明と一致する。
